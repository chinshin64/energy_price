# 平台安全能力验证执行计划

> **内部敏感 · 严禁泄露或外传**

**版本**：v1.0  
**制定日期**：2026-07-16  
**执行节点**：172 受控服务器（172.23.25.54）  
**约束**：所有动态请求测试在 172 上执行；每项最多 5 次业务请求

---

## 一、前置准备（P0-blocker）

| 步骤 | 内容 | 完成标准 |
|---|---|---|
| P-01 | 恢复 172 SSH 连通性 | `ssh server-172` 可达，确认受控出口 IP |
| P-02 | 检查 172 上的测试脚本和依赖 | Node.js 运行时、脚本副本、配置文件就绪 |
| P-03 | 确认各平台授权材料有效性 | 滴滴 secdd token、特来电凭证、星星充电微信身份、新电途登录材料、团油/快电/云快充凭证 |
| P-04 | 确认 172 出口 IP 和网络路由 | 记录受控出口，确保不是内网直连 |

> **P-01 是全局阻塞项**，连不通 172 无法启动任何验证。

---

## 二、执行批次划分

按「同平台同链路可复用」原则分批，减少登录态浪费和链路重建开销。

### 第一批：最高优先级（6 项）

#### 批次 1A — 滴滴身份与设备验证（DIDI-01 + DIDI-02）

| 项 | 内容 |
|---|---|
| 清单 ID | DIDI-01, DIDI-02 |
| 能力 | 核心查询强制确认真实用户 + 核心查询使用真实设备风险结果 |
| 前置 | secdd 初始化已验证(success)，turingCore 真实设备令牌被 blocked |
| 执行步骤 | 1. 在 172 上用有效 secdd token 发起核心查询（1 次）→ 记录正常基线 |
| | 2. 退出登录状态后重发同一查询（1 次）→ 观察是否被拒绝或降级 |
| | 3. 用过期/篡改 token 重发（1 次）→ 观察服务器处置 |
| | 4. 修改设备标识字段后重发（1 次）→ 观察是否触发风险处置 |
| | 5. 如步骤 4 无变化，用完全缺失设备字段重发（1 次）→ 观察降级 |
| 请求预算 | 5 次（DIDI-01 和 DIDI-02 共享） |
| 复用 | 为 DIDI-03/04/05 建立基线 |
| 通过标准 | DIDI-01: 无效状态被拒绝或减少返回；DIDI-02: 设备异常触发明确处置 |
| 依赖 | turingCore blocked 状态需要先尝试在 172 上获取新令牌 |

#### 批次 1B — 星星充电逐次请求证据（STAR-01）

| 项 | 内容 |

#### 批次 1C — 新电途全新登录与请求验证（XDT-01 + XDT-02）

|---|---|

## 四、每项验证必须记录的字段

| 字段 | 说明 |
|---|---|
| 清单 ID | 对应 backlog 中的 ID |
| 测试时间 | ISO-8601，精确到秒 |
| 执行节点 | 172 + 受控出口 IP |

| 证据文件 | 请求级摘要文件路径 |
| 新证据状态 | 已验证 / 部分验证 / 未验证 / 已确认缺失 |
| 追加目标 | `data/platform-security-test-history.json`（追加，不覆盖）|

## 五、风险与注意事项

1. **172 连通性是全局阻塞项** — 当前 SSH 超时，需先排查网络/VPN
2. **turingCore blocked 状态** — DIDI-02 依赖真实设备令牌，需先在 172 上尝试获取新令牌
3. **授权材料时效** — 各平台 token/凭证可能已过期，执行前需验证
4. **5 次限制是硬约束** — 不允许多发请求"试探"，每次请求都要有明确目的
5. **证据脱敏** — 不保存完整凭证、签名值、用户隐私，只存摘要
6. **同平台批次可合并执行** — 如果链路稳定，1A+2A+3A 可在一次会话中完成
