## 一、wsgsig 签名结构逆向分析

### 1.1 整体格式

```
dd05-<Base64编码的二进制载荷>[##<可选后缀>]
```

| 组成部分 | 说明 |
|---------|------|
| `dd05-` | 版本标识前缀，"dd"=滴滴，"05"=协议版本号 |
| Base64载荷 | 核心签名数据，解码后118~542字节不等 |
| `##`后缀 | 可选，102/2012条包含，两种类型（见1.4节） |

### 1.2 二进制载荷结构（解码后）

通过对比1910条长签名（>700字符，解码约530字节）的二进制结构，发现**固定段与可变段交替排列**的模式：

| 偏移量 | 长度 | 类型 | Base64可见 | 推测含义 |
|--------|------|------|-----------|---------|
| 0-8 | 9B | 可变 | 首段变体 | 随机Nonce/IV |
| 9-12 | 4B | **固定** | `Kqt5Hft` | 协议Magic Number |
| 13-45 | 33B | 可变 | 第二变体段 | 加密的请求参数（含坐标） |
| 46-47 | 2B | **固定** | `1EFu` | 协议帧标识 |
| 48-72 | 25B | 可变 | 第三变体段 | 加密的会话信息 |
| 73-79 | 7B | **固定** | `aLA/CAene0` | 协议帧标识 |
| 80-89 | 10B | 可变 | — | 加密数据 |
| 90-95 | 6B | **固定** | `sgMV/E8/So` | 协议帧标识 |
| 96-104 | 9B | 可变 | — | 加密数据 |
| 105-111 | 7B | **固定** | `+VtB9es/E6` | 协议帧标识 |
| 112-120 | 9B | 可变 | — | 加密数据 |
| 121 | 1B | **固定** | — | 帧标识 |
| 122 | 1B | 可变 | — | 标志位 |
| 123-127 | 5B | **固定** | `/C9aTfb` | 帧标识 |
| 128-137 | 10B | 可变 | — | 加密数据 |
| 138-140 | 3B | **固定** | `z63lB` | 帧标识 |
| 141-152 | 12B | 可变 | — | 加密数据 |
| 153-159 | 7B | **固定** | `6XgHaeiBCK` | 帧标识 |
| 160+ | ~370B | 可变 | — | 加密的签名主体/HMAC |

**关键发现**：
- 固定段共42字节（占前527字节的8%），为协议版本/帧标识
- 可变段占92%，且**同一Nonce始终产生相同的后续字节**（确定性加密）
- 偏移13-45的可变段与坐标存在强相关性但不完全确定性（同一坐标314/778种不同编码）

### 1.3 签名长度分布

| 签名类型 | 原始长度 | 解码长度 | 数量 | 场景 |
|---------|----------|---------|------|------|
| 短签名 | 208字符 | ~118字节 | 45条 | 列表请求（无token，pageNo≥3） |
| 中签名 | 208-700字符 | 156-528字节 | 57条 | 列表请求（低页码） |
| 长签名 | 700-728字符 | 525-542字节 | 1910条 | 详情请求（94%）+ 列表请求 |

**长度与scope关系**：detail签名平均705字符，list签名平均517字符。detail请求携带更多加密参数。

### 1.4 `##`后缀分析

102条签名包含`##`分隔符，存在两种后缀类型：

**类型A：MD5设备指纹（67条）**
```
NTc5YmEzOTRiYWMzMWUxNDgyYzE3MGY4MTQ3YzczZjk
→ Base64解码 → "579ba394bac31e1482c170f8147c73f9"（32位hex = MD5）
```
- 跨4城市共享同一MD5，为**设备/安装级唯一标识**
- 主要出现在短签名和列表请求中

**类型B：加密会话令牌（35条）**
- 44字符，Base64解码为33字节二进制
- 每个tokenId对应不同的令牌值
- 为**会话级加密数据**

### 1.5 加密机制推断

| 证据 | 推断 |
|------|------|
| 前9字节随机Nonce，后续确定性 | 使用**带IV的对称加密**（AES-CBC或类似） |
| 固定段跨所有城市一致 | 固定段为**协议硬编码**，非加密数据 |
| 同一坐标产生不同密文 | IV不同导致密文变化（CBC模式特征） |
| 偏移273处有高频固定段（1565/2012） | 加密输出的**明文固定段**在特定位置 |
| `openid=general_app`（1878/2012） | 使用**通用匿名openid**，非真实用户 |

## 二、AI签名生成可行性评估

### 2.1 逆向微信小程序JS代码

| 维度 | 评估 |
|------|------|
| 可行性 | ⚠️ 理论可行，实操困难 |
| 难点1 | 微信小程序打包为wxapkg格式，需脱壳解包 |
| 难点2 | JS代码经过混淆压缩，变量名无意义 |
| 难点3 | 签名逻辑可能在Native层（JSCore/Native Plugin），JS层只是调用入口 |
| 难点4 | 加密密钥可能硬编码在Native SO库中，非JS可读 |
| 工时估算 | 2-5人日（仅JS层）/ 5-10人日（含Native层） |

**结论**：可作为探索方向，但不保证能获取完整签名算法。若签名核心在Native层，则JS逆向只能获取调用接口而非实现。

### 2.2 模式学习生成签名

| 维度 | 评估 |
|------|------|
| 可行性 | ❌ **不可行** |
| 原因1 | 签名核心是**加密运算**（输入→加密→输出），不是统计模式 |
| 原因2 | 9字节随机Nonce使同一输入产生不同输出，无法建立确定性映射 |
| 原因3 | 可变段的加密密文在Base64字符空间均匀分布，无统计特征可学 |
| 原因4 | 即使学习到固定段的位置，也无法生成正确的加密段 |

**结论**：模式学习对加密签名完全无效。这不是模式识别问题，而是密钥恢复问题。

### 2.3 Frida/Xposed Hook微信进程

| 维度 | 评估 |
|------|------|
| 可行性 | ✅ **最可行的实时签名方案** |
| 实现路径 | Root Android设备 → 安装Frida → Hook微信签名函数 → 按需调用 |
| 优点1 | 无需逆向算法，直接获取签名结果 |
| 优点2 | 可自动化，搭建签名服务供爬虫调用 |
| 缺点1 | 需要Android设备（物理或模拟器）常驻运行 |
| 缺点2 | 微信版本更新可能导致Hook点失效 |
| 缺点3 | 需要维持微信登录态（ticket/token） |
| 工时估算 | 3-5人日（首次搭建） |

**结论**：这是唯一可靠的实时签名生成方案。核心挑战是维持微信登录态的稳定性。

### 2.4 Node.js复现签名逻辑

| 维度 | 评估 |
|------|------|
| 可行性 | ❌ **不可行**（无密钥） |
| 前提条件 | 需完整逆向出加密算法 + 获取加密密钥 |
| 瓶颈 | 密钥极可能在Native层，JS逆向无法获取 |
| 若获取密钥 | 可在Node.js中用crypto模块复现，工时1-2人日 |

**结论**：以当前信息无法在Node.js中复现。密钥是硬伤。

### 2.5 替代方案：签名语料热更新

| 维度 | 评估 |
|------|------|
| 可行性 | ✅ **最实用的短期方案** |
| 实现路径 | 定期从WAF日志导出 → 运行build-didi-signature-corpus.py → 替换语料库 |
| 优点 | 无需逆向，利用现有基础设施 |
| 缺点 | 依赖WAF日志的持续可用性和更新频率 |
| 建议 | 自动化：每日定时拉取WAF CSV + 重建语料 |

## 三、攻击面分析

### 3.1 签名过期风险 ⛔ 严重

| 指标 | 现状 |
|------|------|
| 语料采集时间 | 2026-05-11（1小时内） |
| 语料生成时间 | 2026-05-28 |
| 当前日期 | 2026-06-08 |
| **已过期天数** | **28天** |

**过期风险分析**：

- **ticket/token有效期**：语料中615种不同ticket，通常微信ticket有效期2小时~7天。**所有ticket极可能已过期**。
- **wsgsig有效期**：签名载荷内可能含时间戳（加密无法确认），但即使签名本身不过期，ticket过期也会导致请求被拒绝。
- **城市风险评估**：4城市风险相同——所有签名来自同一天的同一小时，**无任何城市有更新鲜的签名**。

**预期影响**：
- 带`ticket`的1878条签名：**大概率已失效**（ticket过期）
- 无`ticket`的125条签名：**可能仍可用**（仅依赖wsgsig）
- 带`_waf_token`的61条签名：**可能仍可用**（WAF令牌独立于用户会话）

### 3.2 签名重放检测 ⚠️ 中等

| 证据 | 分析 |
|------|------|
| 20/2012条签名完全重复 | 服务端**未严格执行**重放检测 |
| 9字节随机Nonce | 服务端**有能力**检测重放（基于Nonce） |
| 重复签名最多3次使用 | 低频重放可能被容忍，高频可能被拦截 |

**建议**：语料中每个签名最多使用1次，优先使用无重复的1992条签名。

### 3.3 签名伪造风险

| 场景 | 风险 |
|------|------|
| AI生成假签名 | **极低** — 需突破加密层，当前AI无法做到 |
| 重放真实签名 | **中等** — ticket过期是主要障碍 |
| Hook实时签名 | **高** — 若实现，可无限制伪造 |

**业务安全影响**：若签名可实时生成，攻击者可：
- 无限制爬取充电站数据（列表+详情）
- 伪造任意城市坐标的请求
- 绕过WAF签名验证层
