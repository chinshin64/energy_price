客户端签名能力滴滴充电微信小程序安全 SDK 本地复现风险

本报告重新梳理一次“直接调用客户端签名模块”的技术实现：客户端包中的安全 SDK 被装入本地兼容运行时，原始请求上下文被重建后可生成结构有效的签名。核心风险不在算法是否被数学破解，而在客户端可执行能力被服务端当作可信身份。

CHAPTER / 01

结论摘要

先回答“发生了什么、为什么重要、这次到底验证到哪里”。

finding
client-trust-01

这不是破解加密算法，而是把原本只能在小程序内运行的签名能力搬到了本地。

实现通过提取小程序主包和安全 SDK 分包模块，补齐 Webpack 风格加载器与必要运行时接口，再使用授权请求语料重建签名输入。安全 SDK 仍然执行原有算法，但执行环境不再受微信小程序边界约束。

ASSESSMENT VERDICT
HIGH

一旦服务端仅凭客户端签名判断“请求来自真实小程序”，攻击者就可能把可复制的软件能力伪装成可信终端。

ROOT CAUSE

客户端持有全部执行能力

签名逻辑、初始化入口和请求包装代码均随客户端分发，具备被提取、装载和调用的条件。

TRUST FAILURE

签名被当作身份而非完整性证据

签名可证明输入经过某段客户端代码处理，但不能单独证明设备、用户、会话和交互过程真实。

CURRENT EVIDENCE

本地签名结构已重新生成

2026-07-10 本地复核成功生成 214 字符、格式符合预期的结果；本次未执行网络访问。

本次验证边界

动态复核只运行本地签名模式，没有设置网络许可开关，也没有向业务接口发送请求。因此“签名模块可被本地调用”是本次确认事实，“服务端当前仍接受该请求”不是本次新增结论。

CHAPTER / 03

安全 SDK 签名技术解读

签名链路由代码载体、兼容运行时、初始化上下文和请求规范化四部分组成。

mechanism
runtime-rehost
SOURCE / 01

小程序代码包

主包包含业务请求包装，安全分包含签名实现与导出入口。

RUNTIME / 02

模块提取

扫描打包后的模块定义，恢复模块编号、参数和函数体。

RUNTIME / 03

兼容加载器

实现模块缓存、导出标记和依赖加载等必要能力。

SIGN / 04

输入重建

把 query 串、body、content-type 和 SDK 控制位恢复为原形。

OUTPUT / 05

签名生成

原 SDK 在本地运行并输出签名，载体位置保持在 query。

签名实际绑定了什么

当前调用形态向 SDK 提交规范化后的 query 参数串、请求体或请求体字符串、内容类型，以及两个 SDK 控制位。业务初始化上下文在签名器加载阶段完成。

签名没有天然证明什么

它没有天然证明请求来自未篡改的微信、真实 Android 设备、真实用户操作或唯一会话。UA、普通 Header 和本地时间戳都可由调用方构造，不能单独作为信任根。

CONTROL FLOW / NON-EXECUTABLE PSEUDOCODE 敏感初始化值与真实模块定位已脱敏 
// 1. 读取主包和安全分包，建立最小兼容运行时
modules = extractModules(MAIN_PACKAGE, SECURITY_PACKAGE)
runtime = createCompatibleRuntime(modules)

// 2. 获取签名导出并初始化业务上下文
signer = runtime.resolve("<REDACTED_SIGNER_MODULE>")
signer.initialize({
  businessId: "<REDACTED>",
  appVersion: "<REDACTED>",
  platform: "mobile-mini-program"
})

// 3. 从授权语料恢复请求形态，旧签名必须先移除
request = rebuildRequestShape(authorizedCorpus)
delete request.query.signature
payload = normalize({
  contentType: request.contentType,
  paramsString: canonicalize(request.query),
  body: request.body,
  runtimeFlags: "<CONTROLLED>"
})

// 4. 仅保留摘要证据，不在报告中输出真实签名
signature = signer.sign(payload)
evidence = summarize(signature) // generated / length / format only
关键判断：只要签名过程不依赖服务端不可导出的秘密或硬件证明，客户端代码被重新托管后就可能继续产生“格式正确”的签名。
CHAPTER / 04

风险复现与绕过路线

按攻击者需要跨越的能力阶段描述。以下为风险路径，不是可直接执行的攻击手册。

attack path
seven stages

获取客户端代码载体

在授权测试环境取得小程序主包和安全 SDK 分包。客户端分发意味着代码最终需要在用户设备可执行，因此无法把所有签名能力永久隐藏。

输入 / WX PACKAGE门槛 / 中

识别签名调用边界

从业务请求包装处定位签名前后的数据流：哪些字段参与签名、签名何时产生、结果放在 query 还是 header，以及初始化发生在哪里。

输出 / CALL GRAPH门槛 / 中

重建最小模块运行时

将主包和分包模块合并到本地加载器，补齐模块缓存、导出定义和依赖解析。目标不是完整模拟微信，而是让签名依赖链能够启动。

输出 / LOCAL RUNTIME门槛 / 高

恢复初始化与输入结构

使用授权语料恢复业务上下文、query 规范化方式、body 表达和 content-type。固定签名不能复用，因此每次请求前重新计算。

输出 / SIGN PAYLOAD门槛 / 中

直接调用原安全 SDK

签名仍由原 SDK 生成，不需要推导算法公式。旧签名先移除，新签名生成后按客户端原始字段分布放回 query。

输出 / WSGSIG-LIKE风险点 / 核心

补齐可伪造的客户端外观

移动端微信 UA、普通浏览器 Header、时间字段和位置参数都可被脚本构造。它们提高请求相似度，但不能提供可信设备身份。

输入 / UA + HEADERS门槛 / 低

受控网络验证

只有在显式许可开关、请求数量上限和统一代理出口同时满足时才允许联网。服务端是否接受签名，需要独立动态证据确认。

控制 / ALLOW FLAG本次 / 未执行

解析响应并映射入库

业务数据从组件列表中提取，按站点 ID 去重后映射为名称、地址、坐标、价格、充电枪数量和来源证据，写入统一 SQLite。

输出 / STATIONS本次 / 未写入

脚本输出结构

验证器只输出模块数量、装载错误数量、语料数量、UA 选择摘要、签名生成状态、长度、格式、输入字段形态和请求字段名列表。真实签名值不会写入标准输出。

为什么不在 HTML 放真实签名

签名是短期安全材料。即使当前可能过期，将真实值、业务初始化常量和可执行脚本合并到可传播文档中，也会不必要地降低复现门槛并扩大泄露面。

CHAPTER / 07

修复路线与验收标准

修复目标不是“让 JS 永远无法被分析”，而是让复制客户端代码仍无法获得等价服务端权限。

defense
server-side trust
P0

服务端签名必须绑定短期会话与一次性挑战

服务端下发带过期时间和单次消费语义的 challenge；签名同时绑定用户会话、请求方法、路径、规范化参数、请求体摘要和 challenge。使用后立即作废。

验收：相同签名重放失败；跨会话、跨路径、跨 body 使用失败；过期 challenge 失败。
P0

把业务授权从客户端签名中拆出来

签名只作为完整性信号，不作为唯一身份凭证。关键数据访问必须同时通过登录态、账户授权、业务权限和服务端风险判断。

验收：无有效业务会话时，即使签名格式正确也无法读取受保护数据。
P1

引入不可由 UA 替代的设备证明

结合平台提供的可信环境证明、设备密钥或服务端注册的密钥对。设备私钥应不可导出，服务端验证证明链和设备注册状态。

验收：仅修改 UA、Header、时间戳和设备字段不能通过设备可信校验。
P1

检测“合法签名 + 非法行为”

对地理跳变、分页深度、请求节奏、会话并发、设备切换、代理出口聚集和数据遍历覆盖率建立联合风险规则。

验收：低频分布式请求仍可通过跨会话关联发现，告警包含设备、账户、出口和空间轨迹。
P2

轮换客户端材料并建设泄露响应

SDK 升级和混淆只能提高分析成本，应配合版本最低要求、服务端兼容窗口、材料轮换和旧版本快速失效机制。

验收：旧版本材料在窗口结束后无法继续访问；轮换不依赖客户端自行声明版本。
